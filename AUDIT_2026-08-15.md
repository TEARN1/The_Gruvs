# Codebase Audit — 2026-08-15

Scope: all **359 source files (~95,194 lines)** in `src/`, plus 5 Supabase edge
functions, every `supabase/queries/*.sql`, and the 116-suite test build — each
checked against the **live** database (`feevvddvrjmfbhffccbf`), not against the
repo's own assumptions.

**Headline: nothing critical or currently exploitable.** Eight real defects, all
of them *silent* — swallowed by a `catch` or a fallback, which is why none of
them shows up as a user-visible error. That is the theme of this audit: the
resilience layer is doing its job so well that it is hiding broken things.

## Findings

### 1. `og-meta` profile route bypasses RLS with no filter — *latent, medium*
`supabase/functions/og-meta/index.ts:233`

The function runs on the **service-role key**, so RLS does not apply. The author
knew this and guarded two of three routes explicitly:

- `handleEvent` → filters `is_published = true` **and** `deleted_at IS NULL`,
  with the comment *"service_role bypasses RLS, so filter explicitly"*
- `handleReel` → filters `is_deleted = false`
- `handleProfile` → **no filter at all**

So a share preview will serve a profile that is soft-deleted (`deleted_at`),
moderation-hidden (`is_auto_hidden`, which the live `profiles_hide_autohidden`
policy exists specifically to hide), or opted out of discovery
(`is_discoverable = false`). All three columns exist live; the policy exists live.

The crawler user-agent check is not a control — `curl -A facebookexternalhit`
defeats it.

Related, same function: `handleReel` ignores `reels.visibility`, so a `private`
reel's `media_url` would be served in a share card. The client explicitly
supports private reels (`reelsDataFlow.js:249`).

**Why it isn't burning today:** I checked the data — 0 profiles are auto-hidden,
0 are soft-deleted, 0 are non-discoverable, and all 10 reels are `public`. This
fires the first time someone is moderated or deletes their account.

### 2. Trust score silently computes on two dead inputs — *real, medium*
`src/services/trustLedger.js:64-71`

```js
const { count: crossingCount } = await supabase.from('path_crossings')
  .select('id', { count: 'exact', head: true })
  .or(`user_id_a.eq.${userId},user_id_b.eq.${userId}`)   // ← neither column exists
  .gte('created_at', ...)                                 // ← nor this one
```

Live `path_crossings` columns are `user_id`, `other_user_id`, `crossed_at`. The
query 400s, and because only `count` is destructured (never `error`), the failure
is completely invisible — `realWorldSocialProof` is **permanently 0**.

Three lines later, `const base = prof.base_trust_index || 50` reads a field that
is neither in the `select()` on line 50 nor a real column on `profiles`, so
`base` is **always 50**.

Net effect: the Social Integrity Score formula quietly runs with two of its
inputs pinned to constants. This feeds ranking and the verification gate.

### 3. Vibe Decay Protocol never runs — *real, medium*
`src/services/dataFlow.js:537`

```js
await supabase.rpc('apply_vibe_decay');
```

This RPC does not exist on the live database, and unlike every other missing RPC
in the codebase it has **no fallback tier**. It doesn't crash anything —
`supabase.rpc()` resolves to `{data, error}` rather than throwing, so
`computeVibeScore` continues normally — but the anti-inflation decay pass has
never once executed. Vibe scores only ever go up.

### 4. Debounced geocode timer survives unmount — *real, low*
`src/components/PostEventModal.js:286`

`geocodeTimer` is cleared on every keystroke (line 285) but has **no unmount
cleanup**, so closing the post-event modal within 1.5s of typing an address
fires `geocodeAddress` → `setGeocoding`/`setLat`/`setLon` on an unmounted
component. This is not theoretical: it produced a real teardown error in
`postEventTour.test.js`.

The same file already demonstrates the correct pattern at line 336
(`return () => { alive = false; clearTimeout(t); }`), so this is a single miss,
not a systemic habit.

### 5. Hashtag table path is permanently dead — *real, low*
`src/components/HashtagStrip.js:46`

Orders by `count`; the live `hashtags` column is `use_count`. The query throws,

### 6. 42 dead fallback RPC tiers — *design smell, low*

**48 of the 115 RPCs the client calls do not exist on the live DB.** That number
sounds alarming and mostly isn't: I checked all 48 call sites, and **42 are the
last tier of a `resilient([...])` cascade whose tier 1 is a working direct table
write.** Reports, RSVPs, profile updates, reel saves, event updates etc. all
function correctly through tier 1.

The cost is not broken features, it's a **false safety net**: when tier 1
legitimately fails (e.g. an RLS denial), the "backup" burns its retry budget on
a function that can never exist, adding latency before the error finally
surfaces.

Deliberate and correctly handled — *not* bugs: `distribute_to_war_chest`,
`get_economic_velocity`, `get_precision_economic_metrics` are each wrapped in
try/catch with an explicit "RPC may not be deployed yet" comment;
`count_path_crossings` and `get_follower_integrity_aggregate` both have working
graceful fallbacks.

### 7. Duplicate React keys in the Upcoming feed — *real, medium* — **FIXED**
`src/utils/startGroup.js:43`

Found while verifying the other fixes in the browser, not in the static pass.
The Upcoming feed logged `Encountered two children with the same key, hdr-month`
inside its `VirtualizedList` — React's own warning says this causes children to
be *"duplicated and/or omitted"*, i.e. rows can render the wrong event.

`insertStartHeaders` only compared each event's bucket against the
*immediately-previous* one, which silently assumes the list is date-ascending.
The root cause of the violation is `collapseTourStops` (`src/services/tours.js`):
it keeps a tour's survivor at **the group's original position** while choosing
the *nearest-upcoming stop* as that survivor — so a tour card can sit early in
the list carrying a later date. Buckets then recur non-contiguously
(month → week → month) and the same `hdr-*` id is emitted twice.

Fixed by emitting each bucket header at most once (a `Set`), which is
behaviour-identical for a correctly sorted list and defensive otherwise, plus a
regression test covering the unsorted case.

> Note the deeper question is left open deliberately: `collapseTourStops`
> breaking date order means a tour card can also appear under a *wrong* header.
> Re-sorting after collapse would change feed ordering, and the caller explicitly
> documents "keep the exact server order" — that is a product call, not a bug fix.

### 8. Nested `<button>` elements — *real, low* — open
Invalid DOM nesting (`<button>` inside `<button>`) from stacked
`TouchableOpacity`s in the `MediaViewer` → `LazyCard` path on the feed. React
logs `validateDOMNesting`. Browsers tolerate it, but it breaks click semantics
and is an accessibility defect (nested interactive controls are not reachable
or announceable). Web-only — harmless on native.

# Addendum — client-side handler audit

Separate pass over every interactive control, asking two questions: does the
handler fire on **both platforms** (web + native), and does a toggle work in
**both directions** (on *and* off, including when the write fails)?

## Platform: clean

| Check | Result |
|---|---|
| `onPress` handlers | 1,170 |
| Web-only DOM handlers (`onClick`, `onMouseEnter`, `onDoubleClick`…) | **0** |
| Unguarded web globals (`window`/`document`/`localStorage`/`navigator`) | **0** — the 3 apparent hits were prose inside comments, not code |

Everything binds `onPress`, which react-native-web maps to click *and* touch, so
no control is web-only or native-only. Nothing to fix here.

## Direction: 4 real bugs (all fixed)

1,095 touchable elements scanned. 6 had no press handler: 4 are deliberate
tap-absorbers (`activeOpacity={1}`, swallowing taps so they don't reach a
backdrop dismiss), 1 was a false positive (handler arrives via `{...authProps}`),
and **1 was genuinely dead**.

### A. `ResidentLiftsSection.js:90` — a button that lied — **FIXED**
"Book via The Resident app" had **no `onPress` at all**, yet `activeOpacity={0.8}`
made it visually depress on tap. It looked and felt like it worked; it did
nothing. Worst kind of dead control — tactile feedback implying success.

`constants/residentUrl.js` already documents the rule, written after a hardcoded
`localhost:3000` shipped to production: *"callers check `hasResident()` and hide
the entry point rather than offering a link that cannot work."* The CTA now
follows the same contract the Stays card in `MapScreen` uses — a real link when
a Resident host is configured, honest text when it isn't. `EXPO_PUBLIC_RESIDENT_URL`
is currently unset, so today it correctly shows text instead of a fake button.

### B. `talentEngine.toggleFollow` reported success unconditionally — **FIXED**
Two compounding bugs meant follow/unfollow could **never** report failure in
either direction — the UI showed "Following" even when the write was denied:

1. `resilient()` **resolves with `fallbackValue`** when every tier fails
   (`resilience.js:324`) — it never rejects. So
   `.then(() => !isFollowing).catch(() => isFollowing)` ran the `.then` on total
   failure, and the `.catch` was **unreachable dead code**.
2. The tiers returned the supabase builder directly, but supabase resolves
   `{ data, error }` instead of rejecting — so even an RLS denial looked like a
   successful tier.

Now each tier throws on `error` (the pattern used elsewhere, e.g.
`RSVPConfirmModal`), and a sentinel `fallbackValue` distinguishes total failure,
so the function returns the state that actually persisted.

> Checked whether this was systemic: it is the only `.then().catch()` chained
> onto a `resilient()` call in the codebase. The two in `RouteJourneyCard` are on
> a supabase builder, which is a different (harmless) thing.

### C. `PlayerProfileModal` left the follower count wrong — **FIXED**
It optimistically bumped `follower_count` but only ever rolled back the *button*
state, so a failed follow flipped the button back while the total stayed
inflated. Now reverts both, with a toast.

### D. `ViberProfileModal` missing its double-fire guard — **FIXED**
`followLoading` was declared and used for `disabled={followLoading}`, but never
checked inside the handler. `disabled` only applies after a re-render, so a fast
double-tap could fire follow and unfollow back to back. Both sibling follow
buttons (`EventDetailScreen:590`, `PlayerProfileModal:83`) already had the
explicit guard; this one was the outlier.

## Minor, noted but not changed

- `SportManagementPanel.toggleLike` — sets a `liking` in-flight flag it never
  reads, so a double-tap can double-fire; `catch { /* handle error */ }` is an
  empty placeholder, so a failed like is silent.
- `ScoutScreen.togglePlan` — toasts "Added to your scout plan!" *before*
  persisting, and swallows an AsyncStorage failure, so the toast can lie.
- `SurveyBuilderModal.toggleActive` — correct in both directions, but gives no
  feedback when the write fails; the switch just doesn't move.

Gold standard for reference: `ProviderDashboardScreen.toggleAvailability`
(optimistic → revert on both `error` and `catch` → in-flight guard → toast in
both directions) and `mediaLikes.toggleMediaLike` (returns a real success
boolean; both call sites roll back on it).

# Addendum 2 — intent audit: do controls honour the promise they make?

Not "does the handler fire" but "does it do what its label says". Highest-
consequence class first: **safety and privacy controls**, where a mismatch is a
harm rather than a bug. Method: take the literal promise in the UI, then trace
whether it is actually *enforced* (server-side where it matters), not merely
*stored*.

## Finding 9 — the map was the one surface not age-rating content — **FIXED**
`src/screens/MapScreen.js:101`

Four of five discovery surfaces apply the viewer-age **content** gate
(`filterByViewerAge`): The Drop, Explore, Scout and Reels. **MapScreen did not** —
it pinned every upcoming event regardless of rating. So the same mature event was
hidden from an under-age viewer in the feed and still visible, by title, on the
map.

To be precise about severity: the **legal** gate was never bypassed — RSVP and
Touch Down both still block in `EventDetailScreen`. This was a content-visibility
inconsistency, not an admission failure.

Fixed by applying the identical gate its four siblings use. `description` was
added to the map's `select` purely so the rating sees the same text signal the
other surfaces do (a tame title can carry a mature description); it is not
rendered.

## Method note

Column drift was checked by extracting each `.from('T')` window **terminated at
the next `.from(`**. This matters: a fixed-size window runs past the following
call and mis-attributes columns — my first pass did exactly that and produced
**119 false positives** (e.g. reporting `events.recipient_id` from what was
actually a `notifications` insert). All 119 were discarded. Reads were then
audited separately from writes, because a bad column in a `.eq()`/`.or()` filter
is invisible to a write-scan — which is precisely how finding #2 had survived.
