1. Where things stand

The Gruvs is a real-time nightlife and social coordination app for South African cities. Its promise is ground truth: who is really at a venue, what's playing, how long the queue is, and how everyone gets home. It's the Play part of a Live · Play · Work ecosystem with The Resident (housing) and Excellency Academy (skills).

The biggest finding in this review

The 9 commits on main from 2 to 4 October added about 12,600 lines and a lot of great-looking screens. 10 of those features are demos: they save to the phone only, use built-in numbers, or try to save to tables that don't exist. Some also tell users things that aren't true: "cryptographically vaulted", "Squad notified", "VERIFIED". The safety panel has been corrected. The rest should be hidden or labelled as previews until they're real. Every push to main deploys the website, so these demos are live on thegruvs.com now. The app already has the switch to hide them (feature() in launchConfig.js).

The five things that matter most right now

  1. Restore the database and merge the branch. Nothing below reaches users until both are done.
  2. Hide or label the demo features, starting with tickets, money and safety.
  3. Choose a payment provider. Every money feature waits on it.
  4. Make Touch Down trustworthy with a rotating door code (section 7.2). It's the heart of "ground truth".
  5. Give Google real pages for events and cities (section 10).

Rules that keep the ecosystem safe

  • Separation comes from database rules, not from headers. The app sends an x-app-id header, but the app sets it itself, so anyone can change it. It's fine as a label. It must never decide who can see what. Each app's tables need their own row-level rules.
  • Sharing data between apps needs consent. Under POPIA, using someone's Resident data in The Gruvs (or passing Gruvs users to Excellency as leads) needs a clear opt-in for that purpose.
  • Cross-app rewards are money-like. Culture Credits earned on Excellency and spent on The Gruvs need the same server-only ledger rules as the wallet (section 9). Never let a phone write a balance.

Why so many features are demos, and the fix pattern

  1. Saved on one phone only. AsyncStorage never leaves the device, so a "squad kitty" is invisible to the squad.
  2. Server saves that can't work. supabase.from(...).insert(...).catch(...) throws, because a Supabase query has no .catch. The surrounding try hides the error, so even a real table would never be written.
  3. Tables that don't exist. ticket_resales, venue_door_queue, talent_escrow, emergency_alerts, safety_pings, lost_and_found and event_flyers aren't in any SQL file. Neither is the function increment_flyer_claims.

Fix pattern for each one: a migration (table plus row rules) → a checked server function → in the app, const { error } = await ... with the error shown to the user → a test. The Meal and the bookings fix from 27 September are working examples.

7.2 Touch Down v2: proof of presence that holds up

Why v2.4's record_touch_down won't work as written: it uses tables that don't exist (venues.location, touch_downs, active_event_nonces). It never checks that someone is signed in. And the location and "accuracy" come from the phone, so checking them on the server doesn't stop someone faking their GPS. Distance is useful evidence, but it isn't proof.

L3
Scanned at the door by staff. Exists today (QRCheckInScanner + secure_check_in). The strongest proof.
L2
Rotating door code (new). A screen at the door shows a 6-digit code or QR that changes every 30 seconds. The phone sends it with the check-in, and the server checks it against the event's secret. You can't fake it from home. This is the real anti-spoofing step.
L1
GPS within 150 m, tightened from about 2 km today, plus app attestation once native. Counts, but weighs less.
L0
Unverified. Still allowed (visibility is a safety feature), but it never earns score or trending weight.
-- sketch: L2 check, on the real table (live_checkins)
create table event_door_secrets (event_id uuid primary key references events on delete cascade,
                                 secret bytea not null);           -- no client access at all
create function touch_down_with_code(p_event uuid, p_code text, p_lat float8, p_lon float8)
returns jsonb security definer set search_path = public language plpgsql as $$
begin
  if auth.uid() is null then raise exception 'not signed in'; end if;
  -- accept the current 30-second window and the one before it (clock drift)
  if not door_code_valid(p_event, p_code, now()) then
    return jsonb_build_object('ok', false, 'reason', 'code expired');
  end if;
  insert into live_checkins (user_id, event_id, lat, lon, verified, verify_level)
  values (auth.uid(), p_event, round(p_lat::numeric, 3), round(p_lon::numeric, 3), true, 2)
  on conflict (user_id, event_id) do update set verify_level = greatest(live_checkins.verify_level, 2);
  return jsonb_build_object('ok', true, 'level', 2);
end $$;

7.3 Offline "Pocket Pass": signed properly

Today's vault "signature" is plain text that anyone can type. A real offline pass works like this:

  1. The server signs (Edge Function) with an Ed25519 private key that never leaves the server. The pass holds the ticket, event, holder, tier and expiry.
  2. Door scanners hold only the public key, synced with the event's revocation list before doors open. They verify with no signal.
  3. Screenshots don't work: the pass shows a short code that rotates every 30 seconds, derived from a per-ticket secret the scanner can check. An animated watermark alone doesn't stop screen recording.
  4. Resale is done by the server: it revokes the seller's pass and issues a new one only after payment clears (section 9).
  5. The phone stores the pass in secure storage (Expo SecureStore), not AsyncStorage.

7.5 Two v2.4 proposals to change

Cross-app tokens (aud "gruvs_api")

One shared Supabase project issues the same kind of token for every app, so custom audiences aren't available. Keep what's built: row-level rules per app, plus app-bound one-time login codes.

Instagram flyer scraping

Against Instagram's terms: it risks account bans and legal claims, and the data is unreliable. Use what promoters send: upload or WhatsApp-forward a flyer, read in the browser (exists), with one-tap admin approval.

9. Money and payments

One decision unlocks seven features

Escrow, Table Pitch-In, the table kitty, ticket resale, Flash Drops, business plan billing and cash-out all need a payment provider. Until there is one, none of them should show prices as if money is moving.

Principles

  1. The provider holds the money, not The Gruvs. Holding customers' money yourselves can make you a regulated payments business. Use the provider's split-payment or marketplace product. Confirm with the provider and a lawyer.
  2. Only the server writes money. The ledger (wallet_transactions) is append-only and clients can't write to it Works.
  3. Payment is confirmed by the provider's webhook, never by the phone. The bookings table already waits for payment_status = 'captured', which only the server can set Works.
  4. Fees are taken in the split (for example 3% on Pitch-In), shown before paying, and itemised on receipts.

Candidate providers

South African options include Paystack, Peach Payments, PayFast and Ozow. Some of them offer Capitec Pay and instant EFT. Compare split-payment support, payout speed, fees, and how refunds and disputes work.

10. Discovery and SEO

Today: the sitemap lists 4 static pages plus upcoming events. When Google opens a share link, it gets a logo, one sentence and an instant redirect, so there is almost nothing to rank. The fix is real pages first, then a rich sitemap.

PhaseWhatResult
0Keep the generated events catalog out of GoogleAvoids a spam penalty for the whole domain
1Full event and profile pages with structured data (Event, Place, Offer in ZAR, performers), a sitemap index, built live and cached hourlyEvents can appear in Google's event results
2City, category, city + category ("amapiano Johannesburg"), venue and "this weekend" pagesThe pages people actually search for
3The Meal, series and tours, sports, reels, recapsFood, sport and video searches
4City guides, IndexNow, generated preview images, more languagesEvergreen content, faster indexing

Quality rules

  • A city, category or venue page exists only with at least 3 real upcoming events. Otherwise it stays out of Google.
  • Never listed: private or crew-only events, reported content, non-discoverable profiles, deleted accounts.
  • Ratings and "going" counts come only from real reviews and real RSVPs.
  • Profiles on Google: organisers, artists and businesses only (recommended, decision 7).

The generated events catalog

globalEventsCatalog.js holds 870 events built from template titles, real venue names and stock photos, and labels them "real authentic events". They aren't happening. Shown as real, they send people to real venues on nights with no event. In Google they'd break its spam rules. Label them as examples or remove them (decision 3), and never list them in the sitemap.
